# IDOR sur `/api/v1/invoices/{id}` permettant de lire les factures de tout client

> ⚠️ EXEMPLE PÉDAGOGIQUE — données fictives, sert de modèle de rapport rempli.

## Résumé

Un utilisateur authentifié peut consulter la facture de n'importe quelle autre
organisation en modifiant l'identifiant numérique de l'URL. L'API ne vérifie pas
que la facture appartient bien à l'organisation de l'appelant.

## Sévérité

**Élevé** — CVSS 3.1 : `7.7` (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`)

Justification : exploitable à distance par tout compte gratuit (PR:L), sans interaction,
fuite de données financières de tiers (C:H).

## Composant affecté

- Endpoint : `https://app.exemple.com/api/v1/invoices/{id}`
- Méthode : `GET`
- Authentification requise : utilisateur standard

## Prérequis

- Victime : org 1043, facture id 8831
- Attaquant : org 1042 (compte gratuit)

## Étapes de reproduction

1. Se connecter avec le compte attaquant (org 1042).
2. Récupérer son token puis appeler la facture d'une autre org :
3. La réponse renvoie la facture de l'org 1043 malgré l'absence de droit.

### Requête

```http
GET /api/v1/invoices/8831 HTTP/1.1
Host: app.exemple.com
Authorization: Bearer <REDACTED-org-1042>
X-Bug-Bounty: mon-pseudo
```

### Réponse

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 8831, "org_id": 1043, "montant": 4200.00, "client": "<REDACTED>" }
```

## Impact

Tout utilisateur authentifié peut énumérer les factures incrémentales et lire les
montants, coordonnées et identités de clients d'autres organisations — fuite de
données financières et personnelles à grande échelle.

## Remédiation proposée

Contrôler côté serveur que `invoice.org_id` correspond à l'organisation du token
avant de renvoyer la ressource (contrôle d'accès au niveau objet).
